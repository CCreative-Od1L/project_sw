# 解锁态内存模型:常驻摘要 + 详情按需解密

**日期**:2026-07-08
**状态**:已接受

## 背景

当前文档已明确两件事:

1. 项目**不防御**已获 root/越狱且可读取运行时内存的攻击者,该风险落在 [SECURITY.md §13](../SECURITY.md) 的边界之外。
2. 即便如此,项目仍要求尽量压缩敏感数据在正常使用路径中的**驻留范围**与**驻留时间**:密钥材料显式清零(见 [ADR-0002](0002-sensitive-data-types.md)),锁定时清零内存明文与密钥(见 [docs/specs/build_roadmap.md §v0.5](../specs/build_roadmap.md))。

现有规格对"解锁后内存里到底常驻什么"仍存在隐含前提:

- [local_search.md](../specs/local_search.md) 以"解锁后内存内线性检索"为基线,默认用户可在内存明文上搜索多个字段;
- [vault_entry.md](../specs/vault_entry.md) 以 `VaultEntry` 作为完整条目明文实体,但未明确它是否应在整个解锁周期常驻;
- 当前实现路线图已默认解锁阶段会批量解密全部条目(见 [build_roadmap.md](../specs/build_roadmap.md) Phase 3b),但没有把"批量解密后保留什么"写成正式决定。

这里需要一个明确的运行时模型,来回答:

- 解锁后是否保留完整 `VaultEntry` 明文常驻;
- 搜索与列表依赖什么工作集;
- 详情页的敏感/半敏感字段如何进入与退出内存;
- 锁定时必须清理哪些对象。

## 考虑过的选项

### 选项 A:完整 `VaultEntry` 明文在解锁期常驻

- 解锁时批量解密全部条目;
- 完整 `VaultEntry` 明文对象(name/url/username/password/notes/custom_fields/...)常驻到锁定;
- 搜索、列表、详情全部直接读这份常驻对象。

优点:
- 数据模型最简单,搜索/列表/详情天然一致;
- 详情页无需再次解密单条;
- 实现成本最低。

缺点:
- 解锁后完整明文在内存中长期驻留,敏感/半敏感字段(`password`、`notes`、`custom_fields`)生命周期过长;
- 与"尽量压缩驻留范围和时间"的目标冲突;
- 容易把详情态明文自然扩散到全局状态。

### 选项 B:摘要常驻 + 字段级多次解密

- 解锁时只提取少量摘要字段常驻;
- 进入详情页后,`password`、`notes`、`custom_fields` 分别按字段单独解密;
- UI 每次显隐敏感字段都可能触发新的解密与 I/O。

优点:
- 内存驻留范围最小。

缺点:
- 字段级重复解密会放大文件读取、AEAD 校验、状态管理和错误处理复杂度;
- 详情页需要维护多段异步/解密状态,实现容易变脏;
- 对当前个人库规模与项目复杂度不成比例。

### 选项 C:摘要常驻 + 单条详情按需解密

- 解锁时允许一次性遍历并解密全部条目,但仅提取摘要字段常驻;
- 详情页进入时按需解密**单条完整详情对象**;
- 详情对象只存在于详情页局部作用域,退出即清理,不得回填全局常驻状态。

优点:
- 比选项 A 显著收缩常驻明文范围;
- 比选项 B 明显更简单,避免字段级重复解密带来的 I/O 与状态复杂度;
- 与当前 vault 格式相容:磁盘仍不暴露明文元数据,摘要仍通过解锁后解密提取。

缺点:
- 解锁阶段仍需遍历并解密全部条目一次以提取摘要;
- 常规搜索范围必须收缩到摘要字段;
- 详情页每次进入都需要解密该条完整详情对象。

## 决定

选择选项 C:**摘要常驻 + 单条详情按需解密**。

### 1. 运行时对象分层

解锁态明确区分两类运行时对象:

1. **常驻摘要模型**:用于列表、排序、过滤、搜索等解锁态常规操作。
2. **详情按需解密模型**:用于详情页展示敏感/半敏感字段,只在详情页局部作用域短生命周期持有。

本 ADR 只规定分层与生命周期,不强制具体代码类名。实现期可选用 `EntrySummary` / `EntryDetail` 等名称,但不得把两者重新混成一个"半懒加载的 `VaultEntry`"。

### 2. 解锁阶段的数据提取

- 解锁阶段允许一次性遍历并解密全部条目;
- 该遍历的目的,不是让完整 `VaultEntry` 在解锁期常驻,而是**提取常驻摘要模型**;
- 提取摘要后,完整条目明文不得保留在全局常驻内存中。

### 3. 常驻摘要模型的字段范围

常驻摘要模型仅包含以下字段:

- `entry_id`
- `name`
- `url`
- `username`
- `favorite`
- `created_at`
- `updated_at`

以下字段**不得**进入常驻摘要模型:

- `password`
- `notes`
- 全部 `custom_fields`(无论 `secret=true` 还是 `secret=false`)

### 4. 常规搜索基线

常规搜索只基于常驻摘要模型执行,因此默认仅覆盖:

- `name`
- `url`
- `username`
- `favorite`(作为按值过滤/置顶条件,非子串匹配)

常规搜索**不覆盖**:

- `password`
- `notes`
- 任意 `custom_fields`

这意味着项目接受一个更窄但更干净的搜索基线,以换取更保守的解锁态内存模型。

### 5. 详情页解密单位

- 详情页按需解密的最小单位是**单条完整详情对象**;
- 不采用字段级多次解密;
- 理由:字段级多次解密会显著放大文件 I/O、AEAD 校验次数、状态管理复杂度和错误路径。

### 6. 详情对象生命周期

- 详情对象只允许存在于**详情页局部作用域**;
- 离开详情页、应用锁定、切后台锁定、或显式隐藏后必须立即清理;
- 详情态明文**不得回填**到全局常驻摘要状态;
- 敏感字段(`password`)是否在详情页内部进一步做"显示/隐藏"控制仍由 UI 卫生规则决定,但无论 UI 是否隐藏,详情对象都不得越过详情作用域泄漏到全局状态。

## 选定理由

1. 该方案承认当前 threat model 的边界:运行时内存被攻陷时无法提供绝对保护,但正常使用路径中仍应主动压缩明文驻留范围和驻留时间。
2. 与"完整 `VaultEntry` 解锁期常驻"相比,该方案显著缩短了 `password`、`notes`、`custom_fields` 的生命周期。
3. 与"字段级多次解密"相比,该方案避免了重复文件读取、重复 AEAD 校验和细碎状态机,对当前项目复杂度更合适。
4. 该方案不要求把 `name` / `url` / `username` 迁成磁盘明文索引,因此不破坏现有"磁盘不暴露明文元数据"的安全基线。
5. 常规搜索范围虽然收缩,但列表/搜索/详情三者的职责边界更清晰:摘要负责定位,详情负责受控读取。

## 实施

- 解锁流水线:
  - 批量解密所有条目;
  - 从每条明文中提取摘要字段;
  - 立即丢弃完整条目明文,只保留摘要集合。
- 搜索流水线:
  - 仅对摘要集合做内存内线性匹配;
  - 不再以 `notes` 或 `custom_fields` 作为常规搜索输入。
- 详情流水线:
  - 进入详情页时按需解密该条完整详情对象;
  - 详情页退出或锁定时立即清理详情对象;
  - 不允许把详情对象写回全局摘要状态。
- 测试要求:
  - 锁定后摘要集合与详情对象均被清理;
  - 搜索仅命中摘要字段;
  - 详情页退出后敏感/半敏感字段不再可从全局状态读取;
  - `password` / `notes` / `custom_fields` 不出现在常驻摘要模型中。

## 影响与后续同步

本 ADR 通过后,以下文档需要同步到新基线:

- [docs/specs/local_search.md](../specs/local_search.md)
  - 删除 `notes` 与 `custom_fields` 参与常规搜索的表述;
  - 明确搜索仅基于摘要模型。
- [docs/specs/vault_entry.md](../specs/vault_entry.md)
  - 区分完整 `VaultEntry` 明文实体与解锁态常驻摘要模型;
  - 调整字段卫生汇总中对列表展示/搜索的描述。
- [docs/specs/build_roadmap.md](../specs/build_roadmap.md)
  - 在 auth/vault/search 实现路径中显式体现"解锁提取摘要 + 详情按需解密"。
