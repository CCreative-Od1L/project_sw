# 本地搜索规格 · PROJECT_SW

> 安全要求概述见 [SECURITY.md §9](../SECURITY.md)。
> 解锁态内存模型见 [ADR-0007](../adr/0007-unlocked-residency-and-summary-detail-split.md)。

搜索方案**已定**:采用解锁后内存内线性检索(基线),不建持久化索引。

## 1. 检索规则

- 检索须在本地完成,不外传任何数据。
- 磁盘上无明文元数据(name/url 均在 `entry_ciphertext` 内),故仅解锁后可搜;解锁阶段会先解密条目并提取**常驻摘要模型**,后续搜索在线性扫描该摘要集合上完成(见 ADR-0007)。
- **匹配语义**:子串匹配 + 大小写不敏感(个人库最直观,在摘要集合上线性匹配零额外索引成本)。
- **可搜字段范围**:仅 `name` / `url` / `username`。
- **favorite(收藏)**:`favorite: bool` 的"可搜"实为按值过滤/置顶,非子串匹配;列表页按 `favorite=true` 置顶展示。
- **搜索结果展示**:搜索命中条目默认仅展示 `name + url + username`;`favorite` 作为列表排序/过滤条件生效,不引入额外展示字段。

## 2. 字段卫生(搜索专属)

- password 不入可搜集合、永不入搜索结果展示——避免搜索成为"瞥见密码"的侧信道。搜索结果默认仅展示 name + url + username;password 仅在条目详情页(受控作用域)按需解密展示。
- `notes` 不入可搜集合。理由不是它天生等于敏感字段,而是 ADR-0007 明确将其排除出常驻摘要模型;常规搜索不为 `notes` 触发按需批量解密。
- 全部 `custom_fields`(无论 `secret=true` 还是 `secret=false`)均不入可搜集合。`secret=true` 与 password 同级;`secret=false` 也不再作为常规搜索输入,以保持摘要模型边界稳定(字段规格见 [VaultEntry 规格](vault_entry.md))。
- 搜索关键词与结果同样遵循日志脱敏要求。
- 若未来引入额外内存索引,锁定/切后台须随摘要集合一并清零。

## 3. 为何不越过基线(已评估)

- 个人库规模(几十~数百条,重使用者上千)下,解锁后线性扫描为微秒~毫秒级、无感知延迟,无性能压力;内存倒排索引仅在 N 极大时才有收益,个人库无价值,故不引入。
- 不对 `notes` 或 `custom_fields` 做常规搜索,是有意接受更窄搜索基线来换取更保守的解锁态内存模型。否则必须在"让这些字段进入常驻内存"与"每次搜索时触发批量按需解密"之间二选一,两者都不符合 ADR-0007 的边界。
- 持久化盲索引(`HMAC(密钥, token)` 落盘)允许解锁前搜索,但:① 仅支持整 token 精确匹配,子串/前缀/模糊匹配全部退化或不可用(HMAC 不可逆)——而用户最常用"输半个词"的子串习惯;② 新增 token 频率/共现泄露面:即便库被锁或文件被窃,攻击者可观"哪些条目共享某关键词片段",这是基线没有的新增泄露;③ 引入独立的盲索引密钥及其管理,绕过 vault 密钥模型。三重代价换来的"省一次指纹解锁"UX 红利过薄(生物解锁已把解锁成本压到一次指纹),不采纳。
